# Unified library v2

All endpoints use existing Bearer authentication and error `{error:{code,message}}`.
`unified-library-v2.json` is a synthetic successful `GET /api/library` response, shared by Mac and Windows. IDs and launch paths are fixtures, not real games.

The approved design's library, metadata CAS, playtime and roots fields remain unchanged. `endedAt` and `lastPlayed` are finite Unix seconds. Metadata revisions start at 0; CAS mismatch is 409. A time event ID is unique per account, across logical games and devices: identical normalized payload retries count once, changed payload is 409. Clients migrating time upload closed PlaySession records with stable event UUIDs (split deterministically when a record exceeds the 86400-second event limit); old personal snapshots are never added to event totals. Account titles override the game's default; v1 admin metadata still changes the default. Collections are account-owned; unknown collection references are rejected.

Additional orchestration:

* `GET /api/admin/library/editions` → `{editions:[{id,canonicalID,candidateID,rootID,relative,signature,entries,savePaths}]}`. Administrator only (401 unauthenticated, 403 nonadmin). Read-only historical published-edition identity inventory: rootID is opaque, relative/entry/save paths are relative, and no server absolute root/state paths or new title-matching fields are exposed. Signature is the edition's STORED publication signature, not the current candidate/source signature; changed source resources/progress do not overwrite the old record. Entries/savePaths retain their original published values. CanonicalID is the existing explicit mapping, or the edition ID when no explicit mapping row exists; reading does not create mappings or inspect sources. All editions remain listed even if the source is offline or the current candidate signature differs. Existing `/api/admin/games` is unchanged.
  For owner-history migration, capture this inventory before publishing a replacement when possible (or distinguish only the explicitly known IDs created by this migration). Compare source identity using candidateID and/or exact `(rootID,relative)`, never title equality or signature equality alone. Retain the old canonical ID only when the controller establishes a UNIQUE old canonical for that identity. Multiple distinct canonical IDs for the same source identity are returned as separate records: leave original data unchanged and require explicit resolution, never choose first/newest. If a newly published empty edition group must be associated with the old canonical, explicitly link it BEFORE uploading account metadata/time/preferences; this endpoint does not link, publish, grant, import history, reset canonical IDs or migrate saves.

* `DELETE /api/library/games/{canonicalID}` → `{}`; authenticated own-account removal, no body (or `{}`). Revokes only the caller's grants for all editions of that canonical game. ANY caller-owned nonclosed canonical lease (including opening, expired-active and revoking) returns 409 without mutation; another account's lease does not block removal. No source or private workspace operation is performed. Saves, time events, metadata/revisions and collections remain intact. Retrying removal of a known canonical game succeeds even with no remaining own grants; unknown canonical IDs return 404. A linked noncanonical ID returns 409. Additional body fields such as userID are rejected (400). Regranting/readding the same editions restores the prior own data; refresh cannot resurrect a removed card without a new grant.
* `DELETE /api/library/collections/{UUID}` → `{}`; authenticated own-account deletion, no body (or `{}`). In one transaction deletes only this account's collection and strips that UUID from every own game metadata membership, including currently removed games; increments each affected game's revision once. Unaffected revisions and other accounts' same-ID collections/memberships are unchanged. Retry succeeds without further revision increments. Additional userID/body fields are rejected (400). Clients should finish their pending metadata pushes first and refresh metadata/revisions after deletion before further CAS updates.

* `GET /api/library/games/{canonicalID}/cover` → existing `{data:base64JPEG,mime:"image/jpeg",sha256}` cover response. Requires access to at least one linked edition; 404 if no default cover exists.

* `POST /api/library/collections {id:UUID,name:string,expectedName?:string|null}` → `{collections:[{id,name}]}` (upsert own collection). Name is trimmed and must contain 1–80 Unicode codepoints, valid UTF-8 and no control characters. Names are casefold-unique per account, excluding the same collection ID; duplicates return 409. Omitted expectedName preserves the unconditional v2 upsert behavior; explicit null is create-if-absent, and a string must exactly equal the current stored name, else 409. Non-string/non-null expectedName is 400. This CAS uses the existing name column, with no added collection revision. Other accounts are independent; legacy v1 personal snapshots are unchanged.
* Scan once via existing admin `POST /api/admin/roots/{rootID}/scan {}`; read persisted account selection state via `GET /api/library/candidates` (administrator only). Response `{candidates:[Candidate]}` retains every existing v1 candidate field and adds exactly `added:boolean` and `ignored:boolean`. `added` is true iff at least one published edition with the SAME candidate ID and CURRENT candidate signature is granted to the current authenticated account. Publishing alone, granting another account, or retaining only an older-signature grant does not mark a candidate added. `ignored` is persisted by `(accountID,candidateID)` and shared across devices/relogin/server restart; rescanning does not reset it. Both flags are independent; the client can render its All/Added/Ignored filters from them. No host source paths are added.
* `POST /api/library/candidates/ignore {candidateIDs:[candidateID],ignored:boolean}` (administrator only) → `{candidates:[Candidate]}` with the same account-state fields. Changes only the CURRENT authenticated administrator's selection state; there is no userID selector. A batch contains 1–100 distinct 32-lowercase-hex candidate IDs; all must exist (including unavailable candidates, which may still be ignored). Unknown IDs return 404, malformed/duplicate/empty IDs or nonboolean ignored return 400. All changes commit in one SQLite transaction, including rollback after any later write failure; repeated requests are idempotent. `ignored:false` clears the state. No scan, publish, grant, or source filesystem operation occurs. Unauthenticated calls return 401; nonadministrators return 403.
* Existing `GET /api/admin/candidates` remains unchanged, without added/ignored fields, for v1 compatibility.
* `POST /api/admin/library/add {candidateIDs:[editionCandidateID],userID:accountID,entryPaths?:{candidateID:entryPath}}` → `{games:[LibraryGame]}`. Admin only. Uses scanned candidates, validates immutable sources and save rules, publishes and grants only the named account; repeat requests retain edition IDs. It does not rescan. Existing custom savePaths publication remains available via v1 admin endpoints. The whole batch validates source snapshots and all v1 save-rule/edition-ambiguity checks before any publication update. Publication, grants and ignored clearing then commit in one SQLite transaction; any batch error rolls them all back, including refreshes of already granted editions. If a successful commit loses its response, retry reuses the same edition IDs. After successful adding, ignored is cleared for these candidate IDs ONLY in the target `userID` account; another administrator/account's ignored state is preserved. Clients refresh `GET /api/library/candidates` after add (the add response remains `{games:[LibraryGame]}`). Optional entryPaths keys must be selected candidate IDs; each chosen safe path must be an actual supported launcher in that candidate and current immutable source. Choices persist for target userID under the actual platform of the resulting edition/canonical, in the same all-or-nothing add transaction. Chosen-path adds preserve the order of existing published entries (newly validated launchers may be appended), never globally reorder another account's languages/entries. A target-account nonclosed canonical lease blocks changing that platform preference (409). Omitted entryPaths leaves prior preferences unchanged.
* `POST /api/library/games/{canonicalID}/launch-preferences {platform,variantID,entryPath}` → `{game:LibraryGame}`. Only the current authenticated account; platform is macos/windows/web. A safe path must exist in an own-granted edition of that canonical and its actual platform. Invalid paths/fields are 400, ungranted or foreign variants are 403, wrong-platform/stale entries or source/edition changes are 409. Reject ANY own nonclosed canonical lease, including opening/expired-active/revoking; another account's lease is independent. Atomically overwrite only this platform preference. `{platform,variantID:null,entryPath:null}` clears only that platform; one null alone is invalid. Reauthorize after source I/O. No global game entry reorder or source changes.
* `POST /api/admin/library/games/{canonicalID}/variants {variantIDs:[editionID]}` → `{canonicalID,variantIDs:[editionID]}`. Admin only; entire explicitly specified groups are linked. Target must be canonical. All affected leases must be closed. Source groups with account metadata/time require explicit future migration and return 409; data is never silently discarded. No title matching or automatic linking.
* `POST /api/library/games/{canonicalID}/session {variantID:editionID,deviceID:string,saveCompatibilityKey?:string}` → unchanged v1 session response. Explicit authorized variant required. No platform guessing at the server. Canonical single writer applies to both v1 and v2 session APIs. Each edition retains its physical workspace and profileKey. A compatibility key requires an active fingerprint-reviewed canonical RenPy mapping. Namespace sessions require request `adapter:"renpy-savedir-v1"`; unaware clients, mismatched keys, stale/unlisted editions and unsafe legacy data return 409. Both routes resolve the same namespace; omission of a key cannot select an isolated fallback. Exact six-field namespace, common/native proof, fixed args/env, registry and cleanup behavior are in `renpy-save-namespace-v1.md`. No key is advertised before review/opt-in. Clients must not imply cross-platform saves are shared when the key is absent.

LibraryVariant may additionally contain `label`, the frozen source-folder display basename, independent of account/custom default titles. It contains no full relative or host path. Version remains omitted unless actually verified; dates/version numbers are not guessed. Label is display only and must never be used to infer identity/linking. Literal `.` entryPaths are accepted only after confirming a registered native entry and actual `.app` source root; Wine/web/other dot selectors are rejected.

LibraryGame optionally includes `preferredEntries:{macos|windows|web:{variantID,entryPath}}`. The map is omitted if there are no currently valid own-granted platform/entry references. These account preferences survive card removal/readd and server restart; they never change another account's defaults or metadata CAS revision. Preserve the existing native-first/default variant selection unless an explicit preference for the requested platform exists; do not use another platform's preference as an override. Source-group linking with stored preferences requires explicit migration, just like existing metadata/time.

V2 platform projection excludes auxiliary executables using the scanner's existing auxiliary-name predicate, including exact case-insensitive basename stems `notification_helper`, `chrome_crashpad_handler`, and `crashpad_handler`. This applies to historical published entries too; it does not rewrite stored entries, edition/canonical IDs, grants, or v1 catalog responses. An edition containing only auxiliary entries retains its logical card with no launchable platform variants. New scans exclude these helpers; similar game names such as `notification_helper_adventure.exe` remain eligible. Filtering uses stored entry names only and performs no source I/O or title matching.

Only granted variants appear in a user's logical card. A single existing edition may contain separate macOS/Windows/web entrances; it appears once per platform with the SAME edition ID and only that platform's entries. Within one canonical game, repeated `id` is allowed ONLY for distinct platform values; `(id,platform)` must be unique. The same edition ID MUST NOT appear under different canonical games. Clients should reject duplicate `(id,platform)` pairs and cross-canonical edition reuse, while accepting a shared edition ID with different platforms within the same game. Never manufacture a new save ID. Platform classification prioritizes `.exe` → `windows` even when its backend is `rpgmz` or `renpy`; only an actual `index.html` path with web/rpgmz backend is `web`. Native/RenPy `.app`, a verified native app-root `.` entry (published folder is `.app`) and explicit RenPy `.py` adapter entries can be `macos`; unrecognized paths/backends are omitted from v2 variants rather than guessed to be macOS. v1 catalog entries are unchanged. Backend `wine` describes a historical executable entry; Windows executes the approved `.exe` natively, subject to client support/isolation checks. The service never changes the OS user's AppData.

`available` reflects the last persisted scan (candidate present and its signature matches the edition), not a guarantee that its source is currently mounted. Session provisioning revalidates paths, signatures, permissions and isolation and fails closed. Public roots contain exactly `{id,title}`; host paths remain confined to existing administrator routes. Existing v1 catalog, personal snapshots, cover and session endpoints remain supported.

Reviewed standalone Windows launch proof is specified in `reviewed-launch-profiles.md`; only the pinned synthetic relative-only executable currently qualifies. That standalone profile does not enable cross-variant saveCompatibilityKey or certify a generic saveIsolation string. Reviewed canonical RenPy namespaces are specified separately in `renpy-save-namespace-v1.md`.
